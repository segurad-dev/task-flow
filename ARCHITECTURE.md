## Слои приложения

### API-слой (`app/routers/`)

Принимает HTTP-запросы, валидирует данные через Pydantic-схемы, вызывает БД/кэш, возвращает ответ. Бизнес-логики минимум — только координация.

### Модели (`app/models/`)

SQLAlchemy 2.0 ORM-модели с `Mapped[]` аннотациями. Только структура данных — никакой логики. Alembic читает эти модели для генерации миграций.

### Схемы (`app/schemas/`)

Pydantic v2 схемы для валидации входных данных и сериализации ответов. Разделение: `Create` (входные данные), `Update` (частичное обновление), `Read` (ответ API).

### Кэш (`app/cache.py`)

Redis-клиент для кэширования списка задач. Ключ `tasks:{user_id}` — у каждого пользователя свой кэш. Инвалидируется при любом изменении задач пользователя.

### Очереди (`app/workers/`)

Celery-задачи для асинхронного выполнения: уведомления и периодические отчёты. RabbitMQ — брокер сообщений, Redis — backend для хранения результатов.

## Поток HTTP-запроса (пример: PATCH /tasks/{id})

```
1. Клиент отправляет PATCH /tasks/42
   заголовок: Authorization: Bearer <jwt>
   тело: {"status": "done"}

2. FastAPI → get_current_user(token)
   - jwt.decode → извлечь user_id
   - db.get(User, user_id) → проверить существование
   - вернуть объект User

3. FastAPI → get_db()
   - открыть AsyncSession
   - передать в обработчик

4. update_task() → db.get(Task, 42)
   - получить текущий статус (old_status)
   - применить изменения: setattr(task, ...)
   - если status=DONE → task.completed_at = now()

5. Если статус изменился → send_notification.delay(...)
   - сообщение уходит в RabbitMQ
   - обработчик не ждёт результата (async)

6. redis_client.delete("tasks:{user_id}")
   - инвалидировать кэш списка задач

7. FastAPI → session.commit()
   - зафиксировать изменения в PostgreSQL

8. Вернуть TaskRead (сериализованный через Pydantic)
```

## Ключевые архитектурные решения

### Почему async SQLAlchemy, а не синхронный?

FastAPI построен на ASGI и использует asyncio. Синхронные операции с БД блокируют event loop, что снижает параллельность под нагрузкой. `AsyncSession` позволяет обрабатывать несколько запросов одновременно в одном процессе.

Компромисс: Alembic не поддерживает async-режим из коробки — в `alembic/env.py` используется синхронный движок через `run_sync`.

### Почему RabbitMQ как брокер Celery, а не Redis?

Redis удобен как dual-use (кэш + брокер), но RabbitMQ даёт:
- подтверждение доставки (acknowledgements)
- приоритеты очередей
- маршрутизацию сообщений

Redis остаётся как result backend — там хранятся результаты задач.

### Стратегия кэширования задач

**Ключ**: `tasks:{user_id}` — у каждого пользователя независимый кэш.

**TTL**: 60 секунд — баланс между актуальностью и нагрузкой на БД.

**Инвалидация**: явная (`redis_client.delete`) при каждом POST/PATCH/DELETE задачи. Выбрана инвалидация вместо обновления, чтобы не рассинхронизировать данные при параллельных запросах.

**Ограничение**: кэш не учитывает параметры фильтрации и пагинации — при первом обращении с фильтром кэш пропускается. Это упрощение допустимо для портфолио-проекта.

### JWT без refresh-токена

Токен живёт 30 минут (настраивается через `ACCESS_TOKEN_EXPIRE_MINUTES`). Refresh-токен не реализован — сознательное упрощение для портфолио. В продакшене необходим механизм обновления токенов без повторного ввода пароля.

### `flush()` вместо `commit()` в роутерах

В роутерах используется `db.flush()` после `db.add()`, а не `db.commit()`. `flush()` отправляет SQL в БД в рамках текущей транзакции и заполняет автоинкрементные поля (id), но не фиксирует изменения. Финальный `commit()` происходит в зависимости `get_db()` после завершения обработчика.

## Структура базы данных

```
users
  id (PK)
  email (UNIQUE)
  username (UNIQUE)
  hashed_password
  created_at

projects
  id (PK)
  title
  description
  owner_id (FK → users.id, CASCADE)
  created_at

tasks
  id (PK)
  title
  description
  status (ENUM: todo/in_progress/done/cancelled)
  project_id (FK → projects.id, CASCADE)
  assignee_id (FK → users.id, SET NULL)
  created_at
  updated_at
  completed_at (NULL до перехода в DONE)
```

Каскадное удаление: `users → projects → tasks`.
